# 临时客户端可信广告与分享事件

## 目的与边界

当前版本不接入广告 SDK 和平台分享 SDK。客户端点击对应按钮后立即视为本地操作成功，随后把成功事件发送给服务端。奖励、每日次数、幂等和账号资产仍必须由服务端决定，客户端不直接增加体力、金币或物品。

该模式只用于联调和阶段性发布。接入正式 SDK 后，应关闭服务端临时可信开关，并恢复服务端回执/回调验签。

## 广告事件

客户端调用 `POST /v1/ads/claim`，并保留现有请求字段以便平滑迁移：

```json
{
  "transaction_id": "32位事件ID",
  "player_id": "当前玩家ID",
  "placement": "energy_restore | settle_double | merchant_item | lottery",
  "provider": "client_trusted",
  "payload": {
    "reward_scope": "奖励业务范围"
  },
  "signature": "",
  "run_id": "仅结算双倍时填写",
  "client_ad_succeeded": true,
  "client_ad_event_id": "与transaction_id相同",
  "ad_platform": "editor | android | ios"
}
```

请求头的幂等键为 `ad.claim:<client_ad_event_id>`。客户端会把未确认的事件 ID 存入本地；网络结果不明确时，再次点击会重用原事件 ID。服务端确认成功后客户端才清除该 ID。

服务端需要在临时可信开关开启时接受 `provider=client_trusted`、空 `signature` 和三个 `client_ad_*` 字段，并按 `(player_id, client_ad_event_id)` 原子幂等：

- `energy_restore`：服务端检查每日次数与体力上限并发放体力；客户端随后读取 `/v1/energy`。
- `settle_double`：`run_id` 必须属于当前玩家且已经完成结算；服务端只补发一次基础金币；客户端随后读取 `/v1/bootstrap`。
- `merchant_item`：广告成功事件先建立一次临时权益，然后客户端调用既有商人领取接口；服务端必须将权益与玩家、商人事件及商品绑定。
- `lottery`：保留为服务端广告位；当前 Go 客户端尚无可用的抽奖报价/开奖接口，因此不会产生实际抽奖请求。

服务端不得采用客户端传入的奖励数量；数量和每日上限均读取服务端配置。建议临时开关按环境控制，并记录玩家、设备、广告位、事件 ID、奖励范围、请求时间和结果。

## 分享事件

体力分享继续使用既有两步接口：

1. `POST /v1/share/create`
2. `POST /v1/share/claim`

两步请求都携带：

```json
{
  "platform": "editor | android | ios",
  "placement_id": "energy_share",
  "client_share_succeeded": true,
  "client_share_event_id": "32位事件ID"
}
```

签到双倍在 `POST /v1/signin/claim` 中携带 `claim_mode=share_double`、`client_share_succeeded=true`、`client_share_event_id` 和 `share_platform`。分享奖励同样由服务端按事件 ID 幂等并执行次数与资格校验。

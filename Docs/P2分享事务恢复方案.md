# P2 分享事务恢复方案

## 目标

在继续使用“客户端直接声明分享成功”的临时方案期间，保证体力分享遇到超时、断网、应用退出或服务端响应丢失后，不会因为客户端生成新的事件 ID 而形成第二次发奖请求。

## 客户端行为

1. 分享步骤完成后，以玩家和 `energy_share` 位置为范围读取待结算事件。
2. 没有待结算事件时创建 32 位 GUID，并在发请求前持久化。
3. `/v1/share/create` 与 `/v1/share/claim` 始终使用同一事件 ID。
4. 收到完整领取结果后清除待结算事件。
5. 超时、断网、HTTP 5xx、限流或幂等冲突时保留事件；下一次点击继续使用原事件 ID。
6. 服务端明确返回达到次数上限或已领取时，结束当前待结算事件并刷新 `/v1/share/status`，不根据客户端计数自行发奖。

签到分享按“玩家 + 服务端 DayKey”生成稳定事件 ID，本身已跨重启稳定，因此无需额外保存待结算记录。

## 服务端约束

- 相同玩家、位置和 `client_share_event_id` 必须返回首次成功结果，不能再次发奖。
- `share.create:<event_id>` 和 `share.claim:<event_id>` 的幂等结果应覆盖客户端重启后的重放。
- 达到每日上限应返回稳定错误码 `SHARE_LIMIT_REACHED`；已消费事件可返回原成功结果，或返回 `SHARE_ALREADY_CLAIMED` 并保证状态接口可查询最终结果。
- 每日限次校验、奖励账本写入和事件消费必须在同一事务中完成。

## 验证

Unity 菜单执行：

`DragonBound > Validation > Validate P2 Share Recovery`

验证内容包括：首次创建、重复读取、错误事件不能清除、成功后下一事件必须更新。

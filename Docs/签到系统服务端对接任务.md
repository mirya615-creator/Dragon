# DragonBound 签到系统服务端对接任务

文档日期：2026-09-03

客户端项目：DragonBound Unity

服务端仓库：`Chalice/DragonBound-server`

当前 OpenAPI：`http://192.168.31.221:8081/openapi.yaml`（v0.13.0）

## 1. 任务目标

完成 Unity 签到系统与服务端的正式数据对接，使签到状态、签到进度、奖励选择、金币/符文发放和每日领取限制均由服务端负责。

分享双倍功能暂时不接可信平台回调：客户端在分享完成后直接向服务端声明“分享成功”，服务端临时信任该事件并发放双倍奖励。后续接入平台验证时再关闭客户端可信模式。

## 2. 当前服务端现状

当前 OpenAPI 已存在：

- `GET /v1/signin/status`
- `POST /v1/signin/claim`

但目前仍有以下阻塞：

1. `cmd/api/main.go` 使用 `signin.UnavailableRewardResolver{}` 和 `signin.UnavailableRewardApplier{}`，因此领取接口会返回 `503 SIGNIN_REWARD_UNAVAILABLE`。
2. `/v1/signin/claim` 当前只接受空请求体或 `{}`，无法传递普通领取、分享双倍及客户端分享成功事件。
3. 状态响应不包含 `cycle_day` 和当日奖励预览，客户端无法使用服务端权威配置展示奖励。
4. 领取响应只有单个 `reward`。双倍符文可能选出两个不同 Rune，因此需要奖励数组。
5. 当前配置系统没有 `signin` 配置段，也没有各环境签到奖励配置文件。

## 3. 签到业务规则

| 签到日 | 基础奖励 |
| --- | --- |
| Day 1 | Gold ×40 |
| Day 2 | Gold ×60 |
| Day 3 | 随机完整 Epic Rune ×1 |
| Day 4 | Gold ×80 |
| Day 5 | Gold ×100 |
| Day 6 | Gold ×160 |
| Day 7 | 随机完整 Legendary Rune ×1 |

规则：

- 7 日循环，第 7 日领取后下一次回到 Day 1。
- 漏签不重置，进度只按成功领取次数推进。
- 每个服务端 DayKey 只能成功领取一次。
- DayKey 根据账号保存的 IANA 时区由服务端计算，不能信任手机时间。
- 符文优先选择玩家尚未拥有的 Rune。
- 同品质 Rune 全部拥有后才允许重复。
- 双倍领取时，金币数量乘 2；符文发放 2 个完整 Rune。
- 双倍符文应优先选择两个不同且未拥有的 Rune；未拥有池不足时按规则回退。
- 客户端不能指定金币数量、奖励类型、品质或 Rune ID。

推荐进度计算：

```text
next_cycle_day = total_signins % 7 + 1
```

奖励解析应基于 `total_signins`，不要依赖会因定义变化而产生歧义的传统连续签到 streak。

## 4. OpenAPI 修改要求

### 4.1 查询签到状态

保留接口：

```http
GET /v1/signin/status
Authorization: Bearer <access_token>
```

目标响应：

```json
{
  "day_key": "2026-09-03",
  "cycle_day": 3,
  "current_streak": 2,
  "total_signins": 2,
  "can_claim": true,
  "preview_rewards": [
    {
      "type": "complete_rune",
      "rarity": "epic",
      "amount": 1
    }
  ],
  "double_available": true
}
```

字段要求：

- `day_key`：服务端当前账号本地日，格式 `YYYY-MM-DD`。
- `cycle_day`：本次可领取的循环日，范围 1～7；当天已领取时可返回刚领取的循环日。
- `total_signins`：历史成功领取总次数。
- `can_claim`：当天是否还能领取。
- `preview_rewards`：当日单倍基础奖励，只描述奖励规则；随机 Rune 预览不提前返回具体 Rune ID。
- `double_available`：当前环境是否开放客户端分享双倍。

### 4.2 领取签到奖励

保留接口：

```http
POST /v1/signin/claim
Authorization: Bearer <access_token>
Idempotency-Key: signin.claim.2026-09-03.<request-id>
Content-Type: application/json
```

普通领取请求：

```json
{
  "expected_day_key": "2026-09-03",
  "claim_mode": "standard"
}
```

客户端分享成功后的双倍领取请求：

```json
{
  "expected_day_key": "2026-09-03",
  "claim_mode": "share_double",
  "client_share_succeeded": true,
  "client_share_event_id": "5e86b225caa54da0b514612850bda8c2",
  "share_platform": "android"
}
```

请求字段约束：

| 字段 | 约束 |
| --- | --- |
| `expected_day_key` | 必填，仅作为跨日并发前置条件；最终 DayKey 仍由服务端计算 |
| `claim_mode` | 必填，枚举：`standard`、`share_double` |
| `client_share_succeeded` | `share_double` 时必须为 `true` |
| `client_share_event_id` | `share_double` 时必填，1～128 字符，用于审计和去重 |
| `share_platform` | `share_double` 时必填，建议枚举：`android`、`ios`、`editor` |

目标响应：

```json
{
  "claim_id": 123,
  "day_key": "2026-09-03",
  "cycle_day": 3,
  "current_streak": 3,
  "total_signins": 3,
  "claim_mode": "share_double",
  "applied": true,
  "replayed": false,
  "rewards": [
    {
      "type": "complete_rune",
      "id": "RUNE_RICOCHET",
      "rarity": "epic",
      "amount": 1
    },
    {
      "type": "complete_rune",
      "id": "RUNE_VOLLEY",
      "rarity": "epic",
      "amount": 1
    }
  ]
}
```

说明：

- `rewards` 必须是数组，以支持双倍符文发放不同 Rune。
- `applied=false, replayed=true` 表示相同幂等请求的成功重放，奖励不得再次写入。
- 如需兼容旧调用，可暂时保留旧 `reward` 字段并返回第一项，但新客户端以 `rewards` 为准。
- 可继续兼容空请求体，将其解释为 `standard`；新客户端统一发送完整请求。

## 5. 临时分享成功机制

本阶段不使用现有 `/v1/share/create`、`/v1/share/claim` 的可信验证流程，因为当前该流程只支持 `expedition_reserve_1`～`expedition_reserve_4` 和 Energy 奖励。

临时处理流程：

```text
用户点击 DoubleBtn
→ Unity 调起系统/平台分享
→ Unity 收到分享完成回调
→ 客户端调用 /v1/signin/claim，claim_mode=share_double
→ 服务端检查客户端分享字段、每日领取状态和幂等键
→ 服务端原子发放双倍奖励
```

必须满足：

- 分享取消或失败时客户端不发送双倍领取请求。
- 服务端不接受客户端上传奖励数量、倍率或 Rune ID。
- 同一 DayKey 无论 `standard` 还是 `share_double`，只能成功领取一次。
- `client_share_event_id` 只能绑定一个玩家和一个 DayKey。
- 服务端记录这是“客户端可信事件”，便于后续审计和关闭旧版本。

建议增加环境配置：

```yaml
signin:
  client_share_trust_enabled: true
  share_double_multiplier: 2
```

当 `client_share_trust_enabled=false` 时，服务端拒绝客户端直接声明分享成功，并返回明确错误码。

## 6. 服务端配置

新增：

```text
configs/development/signin.yaml
configs/staging/signin.yaml
configs/production/signin.yaml
```

建议结构：

```yaml
signin:
  cycle_days: 7
  client_share_trust_enabled: true
  share_double_multiplier: 2
  rewards:
    - day: 1
      type: gold
      amount: 40
    - day: 2
      type: gold
      amount: 60
    - day: 3
      type: complete_rune
      rarity: epic
      amount: 1
      prioritize_unowned: true
    - day: 4
      type: gold
      amount: 80
    - day: 5
      type: gold
      amount: 100
    - day: 6
      type: gold
      amount: 160
    - day: 7
      type: complete_rune
      rarity: legendary
      amount: 1
      prioritize_unowned: true
```

配置加载器需要增加 `SigninConfig`，并校验：

- Day 1～7 必须完整且不能重复。
- 金币和 Rune 数量必须大于 0。
- Rune 品质只能使用服务端已发布品质。
- 倍率只能大于等于 1，当前最大值固定为 2。
- staging/production 必须显式配置，不能静默回退 development。

## 7. 奖励事务要求

一次领取必须在同一数据库事务中完成：

1. 锁定或创建玩家签到 Profile。
2. 计算服务端 DayKey。
3. 校验 `expected_day_key`。
4. 校验当天是否已经领取。
5. 校验幂等记录。
6. 计算 `cycle_day` 和服务端奖励。
7. 分享双倍时校验临时客户端分享事件字段。
8. 金币写入资源账本，或创建完整 Rune 实例。
9. 写入 `signin_claims.reward_data` 奖励快照。
10. 更新 `total_signins`、`last_claim_date`。
11. 写入幂等结果并提交事务。

任何一步失败必须整体回滚，不能出现“签到已记录但奖励未到账”或“奖励到账但还能再次领取”。

随机 Rune 的最终 ID 必须写入奖励快照。幂等重放时直接返回原奖励，不得重新随机。

## 8. Rune 选择规则

服务端从目标数据库已发布 Rune 中选择，不能使用客户端 Rune 列表作为权威数据。

选择流程：

1. 获取指定品质全部已发布 Rune，按稳定字段排序。
2. 查询玩家已拥有的完整 Rune。
3. 优先建立未拥有候选池。
4. 候选池非空时只从未拥有池选择。
5. 候选池为空时允许从完整品质池重复选择。
6. 双倍奖励选第二个 Rune 时，将第一个选择结果视为本次已经拥有，优先避免同次重复。
7. 使用稳定的服务端随机种子或将最终结果持久化，保证重试结果一致。

## 9. 错误码要求

| HTTP | code | 客户端处理 |
| --- | --- | --- |
| 400 | `SIGNIN_DAY_KEY_CHANGED` | 重新查询状态并刷新界面 |
| 400 | `SIGNIN_TIMEZONE_INVALID` | 提示账号时区异常 |
| 400 | `SIGNIN_SHARE_EVENT_REQUIRED` | 分享双倍参数缺失，恢复按钮 |
| 403 | `SIGNIN_CLIENT_SHARE_DISABLED` | 当前版本不能直接声明分享成功 |
| 409 | `SIGNIN_ALREADY_CLAIMED` | 重新查询状态，按当天已领取处理 |
| 409 | `IDEMPOTENCY_CONFLICT` | 不自动换键重试，记录 trace_id |
| 422 | `SIGNIN_REWARD_REJECTED` | 配置或奖励异常，禁止发奖 |
| 429 | `RATE_LIMITED` | 客户端退避，禁止连续点击 |
| 503 | `SIGNIN_REWARD_UNAVAILABLE` | 保持领取资格，允许稍后重试 |

所有错误继续使用统一 `ErrorResponse`，包含 `code`、`message`、`trace_id`。

## 10. 日志、指标与审计

服务端日志建议包含：

- `player_id` 的安全标识或内部 ID；
- `day_key`、`cycle_day`、`claim_mode`；
- `claim_id`、幂等键摘要、是否重放；
- 奖励类型、最终 Rune ID、数量；
- `client_share_event_id`、平台、客户端版本；
- `trace_id`、响应码、事务耗时。

建议指标：

- `signin_status_requests_total`
- `signin_claim_requests_total{mode,status}`
- `signin_claim_success_total{mode,reward_type}`
- `signin_claim_replay_total`
- `signin_claim_conflict_total`
- `signin_reward_apply_failures_total`
- `signin_client_share_claim_total{platform}`
- `signin_claim_duration_seconds`

## 11. 服务端测试要求

至少覆盖：

1. 新玩家第一次状态为 Day 1，可领取。
2. Day 1～Day 7 奖励配置正确。
3. 第 8 次领取循环到 Day 1。
4. 漏签多天后进度不重置。
5. 同一 DayKey 第二次领取返回 409。
6. 相同幂等键重试返回原结果且不重复发奖。
7. 不同幂等键并发领取只有一次成功。
8. 请求期间跨日时 `expected_day_key` 不一致，不领取错误日期奖励。
9. 普通金币领取正确写入资源账本。
10. 双倍金币领取数量为基础值的 2 倍。
11. Epic/Legendary Rune 优先选择未拥有项。
12. 双倍 Rune 优先发放两个不同未拥有 Rune。
13. 同品质全部拥有后允许重复。
14. 分享失败字段或缺少事件 ID 时不能双倍领取。
15. `client_share_trust_enabled=false` 时拒绝客户端成功声明。
16. 奖励写入失败时签到记录、奖励和幂等记录全部回滚。
17. 无效时区、无效 Token、限流和数据库异常返回正确错误码。

## 12. 联调验收标准

- Unity 进入 Main 场景时能够从服务端获取 DayKey、循环日和奖励预览。
- 当天未领取时 SignPanel 正常显示；当天已领取时不重复显示领取状态。
- 普通领取后服务端金币或 Rune 数据正确变化。
- 客户端分享成功后双倍领取正确，分享取消不发奖。
- 领取成功后调用 `/v1/bootstrap` 和 `/v1/runes` 能读取最新资产。
- 断网、超时后使用相同幂等键重试不会重复发奖。
- 客户端修改金币数量、Rune ID、倍率或本地时间不能影响服务端奖励。
- 服务端日志能够通过 `trace_id` 定位一次完整领取。
- OpenAPI 与实际处理器、请求/响应 DTO 保持一致。

## 14. 后续替换项

客户端直接声明分享成功仅用于临时联调，不能视为防作弊方案。接入正式平台分享验证后：

1. 关闭 `client_share_trust_enabled`。
2. 将 `client_share_event_id` 替换为服务端签发并验证的分享凭证。
3. 保持 `/v1/signin/claim` 的 `share_double` 业务语义不变。
4. 服务端在签到事务中消费可信分享凭证，避免重复使用。

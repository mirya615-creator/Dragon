# DragonBound 段位结算服务端修改说明

## 1. 修改目标

修复以下线上问题：

- 新账号第一局胜利后不加星。
- 后续胜利的段位更新看起来滞后一局，表现为“每两局才结算一次”。
- 游戏失败或主动退出后需要扣除 1 星。
- 同一局因超时、断线或客户端重试重复提交时，只允许结算一次。

段位属于账号持久数据，正式环境必须由服务端权威结算。客户端只提交对局结果并展示服务端返回的段位快照，不在本地直接修改线上段位。

## 2. 当前客户端行为与已定位问题

当前客户端使用 Go 在线服务模式。

### 2.1 对局结束接口

- 开始对局：`POST /v1/runs/start`
- 胜利结算：`POST /v1/runs/{run_id}/finish`
- 失败结算：当前客户端会进入 `POST /v1/runs/{run_id}/quit`
- 主动退出：`POST /v1/runs/{run_id}/quit`
- 查询段位：`GET /v1/rank`

客户端收到在线结算结果后会设置：

```text
ApplyRank = false
ServerAuthoritativeSettlement = true
```

也就是说，客户端不会再执行加星或扣星，而是假定 `/finish` 或 `/quit` 已经在服务端完成段位结算。

### 2.2 当前接口缺口

现有 `finish` 返回结构只有金币、符文和商人事件等结算信息，没有本局段位变化和结算后的段位快照。客户端返回 Main 场景后只能重新请求一次 `GET /v1/rank`。

由此会产生两类问题：

1. 如果 `/finish`、`/quit` 没有写入段位，胜负永远不会改变星数。
2. 如果写入与读取不是强一致，或 `GET /v1/rank` 请求失败，Main 会显示旧段位，看起来像隔一局才更新。

## 3. 服务端必须实现的结算规则

### 3.1 胜负对应变化

| 对局结果 | 段位变化 |
| --- | ---: |
| 正常胜利 | `+1` 星 |
| 正常失败 | `-1` 星 |
| 玩家主动退出 | `-1` 星 |
| 超时并判负 | `-1` 星 |
| 服务端故障、无效对局、NoContest | `0` 星 |
| 相同 `run_id` 的重复请求 | 返回第一次结果，`0` 次额外变化 |

最低保护仅指星数不能小于零：玩家处于 `RANK_01 / segment 1 / stars 0` 时失败或退出，仍保持该状态。

本需求不采用 Recruit～Corporal 失败不扣星的旧客户端保护规则；所有段位均按失败或退出扣 1 星处理。

### 3.2 当前段位结构

- `RANK_01`～`RANK_09`：每个大段包含 3 个小段。
- `RANK_01`～`RANK_03`：每个小段需要 3 星。
- `RANK_04`～`RANK_06`：每个小段需要 4 星。
- `RANK_07`～`RANK_09`：每个小段需要 5 星。
- `RANK_10`：不再分小段，继续累计额外星数。

从 `RANK_01` 起累计 108 星进入 `RANK_10`：

```text
RANK_01..03: 3 ranks × 3 segments × 3 stars = 27
RANK_04..06: 3 ranks × 3 segments × 4 stars = 36
RANK_07..09: 3 ranks × 3 segments × 5 stars = 45
Total                                           = 108
```

建议服务端以 `total_rank_stars` 作为唯一可写入的标准值，再由它推导 `rank_id`、`segment` 和当前小段 `stars`，避免跨小段升降时出现状态组合错误。

计算规则：

```text
win:  total_rank_stars = min(MAX_INT64, total_rank_stars + 1)
lose: total_rank_stars = max(0, total_rank_stars - 1)
quit: total_rank_stars = max(0, total_rank_stars - 1)
```

## 4. 推荐的事务与幂等实现

`/finish` 和 `/quit` 应调用同一个内部段位结算方法，例如：

```go
ApplyRunRankResultTx(ctx, tx, playerID, runID, outcome)
```

建议在同一数据库事务内完成：

1. 按 `run_id` 锁定对局记录。
2. 验证该对局属于当前认证玩家。
3. 验证对局结果合法且允许结算。
4. 查询 `rank_settlement` 是否已经存在该 `run_id`。
5. 如果已经结算，返回第一次保存的段位结果，不再次修改星数。
6. 锁定玩家段位记录；新账号不存在记录时初始化为总星数 `0`。
7. 根据结果计算 `star_delta`：胜利 `+1`，失败或退出 `-1`，无效对局 `0`。
8. 更新玩家段位，并推导新的 `rank_id`、`segment`、`stars`。
9. 写入本局段位结算记录。
10. 同步排行榜所需字段。
11. 与金币、符文等本局奖励一起提交事务。

建议的唯一约束：

```sql
UNIQUE KEY uk_rank_settlement_run_id (run_id)
```

建议结算记录至少保存：

```text
run_id
player_id
outcome
star_delta
before_total_rank_stars
after_total_rank_stars
before_rank_id / before_segment / before_stars
after_rank_id / after_segment / after_stars
promoted
demoted
settled_at
```

不要采用“先返回结算成功，再异步更新段位”的方式。`/finish` 或 `/quit` 返回 `Settled` 时，紧接着的 `GET /v1/rank` 必须能读到本次结算后的数据。

## 5. 接口返回结构修改

### 5.1 `/finish` 和 `/quit` 返回段位快照

建议在现有响应中增加 `rank_settlement`：

```json
{
  "run_id": "run-123",
  "result": "win",
  "settlement_status": "Settled",
  "settlement": {
    "base_gold": 20,
    "ad_multiplied": false,
    "total_gold": 20,
    "rune_fragments": 0,
    "rune_drops": []
  },
  "rank_settlement": {
    "applied": true,
    "replayed": false,
    "star_delta": 1,
    "before": {
      "rank_id": "RANK_01",
      "segment": 1,
      "stars": 0,
      "total_rank_stars": 0
    },
    "after": {
      "rank_id": "RANK_01",
      "segment": 1,
      "stars": 1,
      "total_rank_stars": 1
    },
    "promoted": false,
    "demoted": false,
    "version": 1
  }
}
```

重复提交同一个 `run_id` 时：

```json
"rank_settlement": {
  "applied": true,
  "replayed": true,
  "star_delta": 1
}
```

这里的 `star_delta` 表示第一次结算实际产生的变化，不表示本次重复请求又修改了一次。

### 5.2 `GET /v1/rank`

建议补充：

```json
{
  "rank_id": "RANK_01",
  "segment": 1,
  "stars": 1,
  "total_rank_stars": 1,
  "version": 1,
  "updated_at": "2026-09-12T10:00:00Z"
}
```

`version` 每次成功改变段位时递增。客户端可以据此拒绝比刚刚结算结果更旧的查询响应。

## 6. 新账号初始化要求

首次创建玩家时，或第一次查询/结算发现没有段位记录时，服务端必须初始化：

```json
{
  "rank_id": "RANK_01",
  "segment": 1,
  "stars": 0,
  "total_rank_stars": 0,
  "version": 0
}
```

第一局胜利必须在该初始值上原子执行 `+1`，返回 `stars: 1`。不能因为段位记录首次创建而跳过本局变化。

## 7. 自然失败与主动退出的兼容说明

当前 Unity 客户端会把所有失败结果都发送到 `/v1/runs/{run_id}/quit`，因此服务端现阶段必须保证 `/quit` 对正常失败和主动退出都执行一次 `-1` 星。

后续客户端会考虑将两者拆分为：

- 自然失败：`/finish`，`result = "lose"`
- 主动退出：`/quit`

无论客户端是否完成拆分，两条路径都必须复用相同的段位事务和幂等表，不能各自独立扣星。

## 8. 错误与异常处理

以下情况不得改变段位：

- `run_id` 不属于当前玩家。
- 对局票据、事件链或结束结果验证失败。
- 对局被判定为 `NoContest`。
- 服务器内部事务失败并回滚。
- 结束请求未达到可结算状态。

如果金币或符文结算失败，段位修改也应随同一事务回滚，接口不能返回 `Settled`。

如果请求超时但事务已经提交，客户端使用相同幂等键重试时，服务端应返回已保存结果。

## 9. 后端验收用例

### 必测用例

1. 新账号初始 `0` 星，第一局胜利后立即为 `1` 星。
2. 连续两局胜利分别得到 `1`、`2` 星，不允许第二局才显示第一局结果。
3. `2` 星失败后变为 `1` 星。
4. `1` 星主动退出后变为 `0` 星。
5. `0` 星失败或退出后仍为 `0` 星。
6. 小段满星后胜利正确进入下一小段。
7. 小段 `0` 星失败时正确退回上一小段最后一星。
8. `RANK_10` 胜利增加额外星；失败减少额外星。当总星数从 `108` 降至 `107` 时，按“所有段位失败均扣星”的规则降回 `RANK_09 / segment 3 / stars 4`。
9. 同一 `run_id` 的 `/finish` 连续提交两次，只增加一次。
10. 同一 `run_id` 的 `/quit` 连续提交两次，只扣除一次。
11. 同一 `run_id` 先 `/finish` 再 `/quit`，第二次不得再次改变段位。
12. 同一 `run_id` 先 `/quit` 再 `/finish`，第二次不得再次改变段位。
13. `/finish` 返回后立即调用 `GET /v1/rank`，两者必须一致。
14. 结算事务失败时，金币、符文、段位和排行榜全部不产生部分写入。

### 并发用例

- 对同一 `run_id` 并发发送 10 个相同结束请求，只结算一次。
- 对同一 `run_id` 并发发送冲突的胜利和退出请求，只允许第一个合法结果落库，其余返回已结算或冲突错误。

## 10. 客户端后续配合项

服务端完成后，请提供更新后的 OpenAPI 文档或响应样例。客户端需要同步：

1. 增加 `rank_settlement` 数据结构。
2. 在结束页面缓存并展示服务端返回的 `after` 状态。
3. 返回 Main 后用 `GET /v1/rank` 做一致性校验。
4. 查询失败时保留刚刚结算成功的段位，不回退显示旧数据。
5. 使用 `version` 防止旧响应覆盖新段位。
6. 补充自然失败与主动退出的原因字段或接口分流。

## 11. 联调完成标准

- 服务端确认 `/finish`、`/quit` 已同步结算段位。
- 响应包含本次变化和结算后段位快照。
- 新账号第一局胜利稳定增加 1 星。
- 每局胜负都立即反映到 Main 页面。
- 重试、断线恢复和重复点击不会重复加星或扣星。
- 排行榜段位与账号段位保持一致。

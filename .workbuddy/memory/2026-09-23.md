## 绕脚后仰_竖向行走无反馈的根因（已分析，未改）
- 直接原因：`UpdateHitShake` 的 `var angle = -hitShakeBackward.x * maxRadians * push;` **只看后向向量的 X 分量**；竖向 lane（前进沿 ±Y）时 `hitShakeBackward ≈ (0, ±1)`，`backward.x ≈ 0` → `angle ≈ 0` → `localRotation` 与补偿位移都≈0，卡原地不动只剩血条。
- 更深的几何原因：Unity 2D UI 的 Z 旋转只能让 sprite 顶部在世界 X 方向位移，**永远不能改 Y**。水平行走时"向后仰"恰好等价于"头往左/右偏"（后向沿 X）所以有效；竖向行走时"向后仰"等价于"头往下/上偏"，Z 旋转做不到。
- 表（行走 → 后向 → 期望头偏 → Z 旋转能否产生）：右(+X)→(-1,0)→-X ✅；左(-X)→(+1,0)→+X ✅；上(+Y)→(0,-1)→-Y ❌；下(-Y)→(0,+1)→+Y ❌。
- 即使把 `hitShakeBackward.y` 加进公式也只能贡献角度，输出位移仍只在 X 轴上，救不了竖向。这是单 RectTransform 节点做"任意方向后仰"的硬限制，不是参数错。
- 用户要求先分析，未让改代码。已列 4 个修法思路：(1) 拆 head/foot 节点（治本，代价最大，要改 V1/V2 prefab，V2 Spine 难处理）；(2) 竖向 case 改整体平移（最简单，丢脚不动语义，本质是被否的整卡后退）；(3) 竖向 lane 绑定时把 sprite 转 90° 让本地 +Y 指向运动轴（治根，要资产/绑定配合）；(4) squash-and-stretch 弹性缩放（任意方向都生效、不改资产、零代码成本，但视觉是"被踩扁"而非"后仰"）。等用户选方向。

## 关键结论：旧抖动"全线路生效" vs 新后仰"仅水平段生效"（同一条路线有横段也有竖段）
- 用户追问核心：为什么旧的左右抖动全线路都行，新的后仰只在横段成立？（附截图证实：小兵无论走竖列还是横行，UI 资源与朝向**完全不变**，永远是同一张正面朝向 sprite）
- 根本差异 = **变换自由度数量**：
  - 旧 = 屏幕空间双轴位移（`anchoredPosition + (sin(p·π·6)·d·att, sin(p·π·8)·d·0.3·att)`），**2 个自由度且完全不需要知道 lane 方向** → 任何线段都必然生效。它的"全线路生效"是设计使然，不是它做对了方向对齐。
  - 新 = 方向相关的屏内旋转，**只有 1 个自由度**：绕 Z 转 θ 时顶部 (0,h/2) → (−sinθ·h/2, cosθ·h/2)，**Y 恒为 h/2，只能沿屏幕 X 移动**。水平段后向沿 ±X，正好落在这个自由度上 ✅；竖向段后向沿 ±Y，落在它够不到的轴上 ❌。
- 第二层原因：美术朝向固定不随行进方向旋转 → sprite 不携带"行进朝向"信息，角色永远面朝观众。所以竖段的"向后仰"在视觉上等价于"人往屏幕上下倒"，**平面对称群里的刚体旋转做不到**（只有绕 X 轴 3D pitch 才行，而 UI 是正交相机，绕 X 轴只会得到垂直压扁，不是倾斜）。
- 结论：即使修正符号、把 `backward.y` 也算进角度，竖段依然无解——问题在"用屏内旋转表达方向性后仰"这个选择本身，不在参数。要任意方向成立必须换算子：位移（2 自由度，脚可不动需拆节点）或压扁/拉伸（squash-stretch）。

- **根因 5 条**：①step 0.20s ≈ 演出 0.217s → **零留白**，动作边界消失，4~6 步连成无缝流水线（方向 C 压短演出后的次生效应）；②**明确 bug**：Bootstrap:1096 传 `interval*0.85f` 做错峰，但 `GreyboxBoardView.RefreshUnits(AiBoardAction,float)`(:701) 首行 `_ = transitionSeconds;` 丢弃 → 错峰从未生效，且后续节奏参数都传不进演出层；③所有动作一刀切 0.2s，Recruit 白等 / FormHero 严重不足 / **UseForgePick 挖掘0.55+擦除 ≈0.62s 被 0.2s 骑住（唯一真重叠、当前最刺眼）**；④等间隔匀速无"决策-行动-消化"曲线；⑤定时器驱动无人手轻重音。
- 方案分层：**P0** 修 transitionSeconds 透传（~10 行，必做，零平衡影响，注意 press 帧额外占 1 帧，`flight = max(0.05, t-0.02)`）；**P1** 新 `Runtime/AI/AiActionPacing.cs` 按 action 类型给间隔（Recruit .22/Move .34/Deploy .42/Merge .50/FormHero .70/UseForgePick .80）×[0.85,1.15] 抖动（必须走 RunRandom 保 AiSurvivalDiagnostics 可复现）；**P2** 逻辑与演出解耦队列（唯一不伤平衡的做法，代价是视图落后逻辑 0.5~1s）；**P3** 拟人微节奏（起手延迟/连招加速/高光留白）。
- **占空比**：Beginner 下现状 5 步=1.00s/1.2s=83%；P1 后 1.98s 若不动决策间隔变 165%（永动），若把 interval 提到 2.4s 则**每波动作数减半→AI 明显变弱**（波次定长，`TwentyWavePressureRuntime.WaveDuration`），无法靠缩放绕开 → 只能靠 P2 解耦。
- P2 主要风险：`board.Changed` 在逻辑提交瞬间触发 `HandleBoardChanged`→无参 `RefreshUnits()` 会让单位先出现在目标格再倒着飞；解法是 AI 侧加 `suppressBoardRefreshForPresentation` 押后单位刷新（现有 `deploymentAnimations`/`pendingHiddenFlightIds` 机制 :829-841 本就是为视图滞后设计的，推广即可）。
- 其他风险：节奏表需放独立 AiActionPacing/Bootstrap 层，**不能写进 BasicUnitAiController**（会波及 `AiDeploymentFormationSymmetryBatch` 无渲染 trace）；V1/V2 两个场景的 `aiBoardActionIntervalSeconds` 要同步改否则 V1 快 V2 慢。
- 产出：`Docs/AI部署节奏优化方案.md`（含数值表、落地顺序、验收清单、风险清单）。

## AI 部署节奏「最小修改方案」（追加到 Docs/AI部署节奏优化方案.md 第八节）
- **关键更正**：飞行动画不会被下一步打断。PlayDeploymentFlight 用挂在 EnsureDeploymentFxLayer 的独立 ghost，被飞单位 SetDeploymentVisualHidden(true)；下次 RefreshUnitsCore 靠 `deploymentAnimations.TryGetValue && HideCommittedView`(:829) 继续隐藏 → 多单位可并行飞。所以 P2 串行队列非必需，「假」的唯一来源是零留白 + 一刀切。
- 核心公式：留白 = 间隔 − 演出。现状 0.20 − 0.217 = **−0.017s（落地与起飞同帧）**。要 0.10s 留白有两条路：抬间隔 / **压短 AI 飞行**（AI 半场距离短，0.20s 本有冗余，平衡代价小得多）。
- M0（1 行）：`DragonBoundBootstrap.cs:40` aiBoardActionIntervalSeconds 0.2 → 0.30（此时 `_ = transitionSeconds` 丢弃 bug 恰好帮我们锁定飞行 0.20）。留白 0.083s。
- M1（+11 行，推荐）：① 删 `GreyboxBoardView.cs:701` 丢弃并透传 flightSeconds；② PlayDeploymentFlight 加 `float? durationSeconds = null` 可选参数，AnimateDeploymentFlight 用它替代常量；③ Bootstrap:1095 改 `interval = GetAiActionInterval(action.Type)` + `RefreshUnits(action, min(0.20, interval*0.55))`；④ 基数 0.2→0.25。分级：Recruit 0.12 / Deploy·Move 0.25 / Merge 0.50 / FormHero 0.70 / UseForgePick 0.85。
- 平衡：典型 5 步周期 1.00s→1.37s（+37%，比 M0 的 +50% 少），每波动作数约 −27%。补偿三选一：难度档位吸收（推荐）/ 提高 stepwiseBasicDeployLimit / 缩短周期冷却（字段名待确认）。
- 坑：V1/V2 的 Greybox_Main.unity 各存一份 aiBoardActionIntervalSeconds，改默认值后两处 Inspector 要同步。

### 最小方案的预期效果与副作用量化（已输出，未改代码）
- 可感知变化：留白 −0.017s → **+0.09s（5~6 帧 @60fps）**，能数出「一下、一下」；Recruit 从 0.20 缩到 0.12 反而更快；Deploy/Move 飞行 0.20→0.1375。
- **重动作不再穿帮**：UseForgePick 铲子动画总感 0.62s，改前 0.2s 后下一步就到（被骑 0.42s），改后 0.85s 余 0.23s 收尾；FormHero 0.70 / Merge 0.50 同理。这是最直观的修复点。
- **副作用（重要）**：Beginner 决策间隔 `AiStrategyProfile.DecisionIntervalSeconds=1.2s`×[0.85,1.15]。改前 5 步周期 1.00s < 1.2s，还有 0.2s 静默；改后 1.37s **已超过 1.2s（占空比 114%）** → 决策间的「思考停顿」消失，动作序列连成不断流。若想保住静默需把决策间隔提到 ~1.6s，代价是每波周期数再减 25%（叠加后 AI 明显更弱）。建议迭代顺序：先上一版跑 AiSurvivalControllerTests + 对拍成型数，接受则可不动决策间隔。

## AI 开局延迟 3 秒方案（Docs/AI开局延迟3秒方案.md，已输出未改码）
- 锚点定为 **MatchState.Running**（Loading 消失、玩家可操作），非 Ready（Ready 还有 InitializationPromptSeconds=1s，且 :786-796 明令 Twenty-wave AI 在 Ready 不能动棋盘）。
- **首次决策时刻 = DecisionIntervalSeconds × rand[0.85,1.15]**（`AiDecisionScheduler` 构造时 Reset 就跑了一次 ScheduleNext，倒计时是满的；Tick 只在 Running 分支调用）→ Beginner 1.02~1.38s、Veteran 0.6~0.8、Elite 0.34~0.46、Master 0.17~0.23（几乎秒发，且随难度漂移 6 倍）。
- 关键约束：第一只敌兵 = Running 后 **StartPreparationSeconds=4.0s**（TwentyWavePressureConfiguration.cs:84/:179）。所以延迟上限必须 <4s，否则 AI 起手晚于敌兵。
- 推荐方案 A：构造函数加 `openingDelaySeconds`，`ScheduleNext()` 首次分支固定用它。**必须 `intervalOrdinal++`**，否则后续决策随机序列整体错位一格，破坏 seed 回放/Recovery 对局。
- 否决方案 B（Bootstrap Update 里加闸门倒计时）：gate 期间 Tick 不被调用、remaining 不递减 → 实际首发 = gate + 1.2s = 4.2s，越过 4.0s。否决 C（塞进 AiStrategyProfile）：违反该类"decision-quality only"契约。
- 新 `[SerializeField] float aiOpeningDecisionDelaySeconds = 3f` 是新增字段，场景文件里没有时取代码默认值 → **不需要去 Inspector 同步**（与旧字段不同）。
- 未覆盖路径：非 Twenty-wave 模式的 `BeginOpeningSequence`（:788-796）在 Ready 就启动，当前两场景都是 useTwentyWavePressureRuntime:1，用不上。

### 方案 A 手工落码要点（2026-09-23 输出步骤，用户手动改）
